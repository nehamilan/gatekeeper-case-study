# What I learned

**1. Put the rules that must never bend in code, not in a prompt.** The identifiable-tier and Indigenous-governance escalations are fixed rules the deterministic layer decides. A prompt can be argued with by a persuasive request. A rule cannot.

**2. Separate "is the document there" from "is the document good enough."** Ethics approval is a presence check a rule can run. Indigenous governance authorization needs authority and judgment, so Gatekeeper never assesses it. Drawing that line early prevented a whole class of false confidence.

**3. Name statuses for what they claim.** I dropped a "rejected" status because only the committee can approve or deny access. "Reject" survived only as a reviewer action on Gatekeeper's recommendation. Labels that overstate authority cause real confusion in a governance workflow.

**4. Define the test key before building.** Writing expected routes, version identifiers, and evidence rows first turned "does it work?" into a comparison. It also exposed gaps in my own spec, such as a case that was missing from the set.

**5. Score a case in groups.** A correct route with the wrong cause is not a pass. Reporting route, evidence, prohibited action, and reasoning separately kept one good result from hiding a bad one.

**6. Ordinary interface choices carry safety weight.** Reviewing the queue and decision card showed how much layout affects the human checkpoint. Active filters need a visible state, a fixed-rule escalation needs a distinct tag from a system failure, and a decision card should not pre-select an action, because a default invites clicking through.

**7. Say what is not measured.** The prototype's model-dependent checks have been run with a real model. I would rather publish that than publish a pass rate I have not earned.
